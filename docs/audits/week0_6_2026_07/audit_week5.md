## 2. Actual backend behavior per question

**Q1 — Claim atomicity / concurrent-claim race.**
`claim_research_run` (`comqutor_alpha/storage/db/repository.py:768-822`) loops up to `_MAX_CLAIM_ATTEMPTS=3` (`repository.py:752`) calling `_claim_research_run_once` (`repository.py:824-899`) inside one `engine.begin()` transaction. The insert of a fresh `queued` row (`repository.py:868-891`) relies on a **real DB-level UNIQUE constraint** on `active_fingerprint` (`comqutor_alpha/storage/db/schema.py:174`, nullable-but-unique so only one non-NULL value per fingerprint can exist) plus the `run_id` primary key (`schema.py:162`). A losing concurrent INSERT raises `IntegrityError` → caught and converted to `_ResearchRunClaimRace` (`repository.py:889-891`) → the whole transaction rolls back → the outer loop re-runs the *entire* decision from scratch (`repository.py:803-819`), so a loser can observe the winner's row and return `reused_in_flight` (or a terminal outcome if the winner already finished). This is genuinely atomic, not a check-then-act race in application code — the DB enforces the mutual exclusion, Python only retries.

Verified empirically, not just read:
- Existing test `tests/test_research_runs_postgres_integration.py:195-247` (`test_concurrent_claims_against_real_postgres_produce_one_created`) fires 4 real threads at a real Postgres instance via `threading.Barrier(4)`; asserts exactly 1 `created` + 3 `reused_in_flight`, single `run_id`. **PASSED** (see §6).
- I independently re-ran this with **8 threads** against the same live Postgres DB (script: `/private/tmp/.../scratchpad/mutation_concurrency.py`, TEST 1) — exactly one `created`, seven `reused_in_flight`, one unique `run_id`. **PASSED**, no double-claim.

**Q2 — Terminal-state overwrite guard.**
Two independent guards, both DB-level conditional UPDATEs (never SELECT-then-write):
- Lifecycle row: `mark_research_run_terminal` (`repository.py:931-976`) checks `is_allowed_transition(row["status"], status)` (`repository.py:954`) against `_ALLOWED_TRANSITIONS` in `comqutor_alpha/research_lifecycle.py:50-56`, which maps every terminal status (`completed`/`partial`/`failed`) to an **empty** transition set — any transition out of a terminal status raises `GraphPersistenceError("RESEARCH_RUN_TRANSITION_INVALID")` (`repository.py:955`).
- Progress row: `update_research_progress` (`repository.py:1259-1308`) has `WHERE research_run_progress.c.current_stage.not_in(("completed","completed_partial","failed"))` (`repository.py:1290-1294`) — a late/out-of-order write to a terminal progress row is a **silent no-op** (`rowcount == 0` → returns `False`), never an overwrite. Same guard duplicated in `mark_research_progress_completed` (`repository.py:1350-1357`) and `mark_research_progress_failed` (`repository.py:1380-1389`).

Verified empirically: mutation script TEST 2/3 forced a real "late" `update_research_progress(..., progress_percent=100, ...)` call against an already-`failed` run on live Postgres — `applied=False`, stage stayed `"failed"`; a second `mark_research_run_terminal(..., status="completed")` on an already-`failed` row raised `RESEARCH_RUN_TRANSITION_INVALID`. **PASSED**.

**Q3 — Retry run_id reuse.**
`_claim_research_run_once` always mints `new_run_id = run_id or str(uuid4())` (`repository.py:868`) for the `created`/`force_refreshed` path; a terminal row's `active_fingerprint` is cleared (`repository.py:964`, `1008`, `1046`) so the fingerprint becomes claimable again, but the NEW claim gets a NEW uuid unless the caller explicitly re-supplies the old `run_id`. Combining an explicit `run_id` with `force_refresh=True` for the *same* fingerprint is explicitly rejected: `if force_refresh and existing["request_fingerprint"] == request_fingerprint: raise GraphPersistenceError("INVALID_FORCE_REFRESH")` (`repository.py:850-851`). Frontend's retry flow (`ProcessingPage.tsx:178-182`) never sends `run_id` on retry at all — only `ticker`/`selected_analysts`/`analysis_date`.
Verified empirically: mutation script TEST 4 (retry via `force_refresh=True` after a terminal `failed` row) minted a distinct uuid; TEST 5 confirmed the explicit-run_id+force_refresh combo on the same fingerprint is rejected with `INVALID_FORCE_REFRESH`. Existing DB test: `tests/test_research_runs_postgres_integration.py:183-192` (`test_terminal_frees_fingerprint_for_new_run_on_postgres`) asserts `retry["run_id"] != claim["run_id"]`. **PASSED** both ways.

**Q4 — SIGTERM/crash vs. genuine algorithm error distinguishability.**
The persisted `error_code` field genuinely distinguishes infra-level termination from in-pipeline algorithm failure:
- Worker crashed (non-zero exitcode, e.g. SIGKILL/unhandled fatal signal): `RESEARCH_WORKER_CRASHED` (`comqutor_alpha/research_jobs.py:469-476`).
- Worker exited 0 but never wrote a terminal DB row (race/bug): `RESEARCH_WORKER_RESULT_NOT_PERSISTED` (`research_jobs.py:491-495`).
- Supervisor-enforced timeout: `RESEARCH_TIMEOUT` (`research_jobs.py:514-516`).
- Graceful server shutdown mid-run: `SERVER_SHUTDOWN` (`research_jobs.py:411,413,447,554,574`).
- Prior-process crash/`kill -9`/reboot discovered at next startup: `SERVER_RESTARTED` (`research_jobs.py:622-650`, wired at `comqutor_alpha/api/main.py:107-115`).
- A genuine in-pipeline exception caught by `execute_claimed_research_run`'s own `try/except` defaults to `INTERNAL_ERROR` (`comqutor_alpha/research_lifecycle.py:834-856`), or a specific pipeline `error_code` if the executor supplied one (`research_lifecycle.py:864`).
All of these are exposed to the API consumer verbatim via `_public_run_record_fields` (`comqutor_alpha/api/routes_research.py:939-964`, `error_code` at line 958) on `GET /api/research/{run_id}/status`, and rendered in the UI (`ProcessingPage.tsx:301-304`, e.g. the existing test literally asserts `RESEARCH_TIMEOUT` renders — `ProcessingPage.test.tsx:163-191`). So SIGTERM/crash and a genuine algorithm bug are **not** collapsed into one indistinguishable code in the common infra-failure cases; they only collapse if the pipeline itself throws a generic unhandled exception (both then read `INTERNAL_ERROR`), which is a real but narrow gap, not a total failure to distinguish.

**Q5 — Progress driven by real step completion, not a fixed/estimated schedule.**
Analyst-level progress (`ResearchProgressReporter.record_analyst_completed`, `comqutor_alpha/research_progress.py:265-287`) is only invoked from `_report_stream_milestones` (`comqutor_alpha/runners/tradingagents_runner.py:156-186`), which is driven by `graph.graph.stream(...)` chunks (`tradingagents_runner.py:338-344`) and only fires `record_analyst_completed` when `final_state.get(report_key)` is a genuinely non-empty string (`tradingagents_runner.py:167-171`) — i.e., real LLM output actually landed in the graph state. Post-analyst milestones (`structured_claims`, `alpha_mapping`, `structure_graph`, `activation_scoring`, `conflict_analysis`, `result_persistence`) are reported via `_report_progress_stage` (`comqutor_alpha/api/routes_research.py:491-501`) called strictly *after* each corresponding real pipeline call succeeds — e.g. `_report_progress_stage(progress_reporter, "structure_graph")` at `routes_research.py:592` runs only after `build_structure_graph_stage(...)` returns without raising (`routes_research.py:587-591`); `"conflict_analysis"`/`"result_persistence"` at `routes_research.py:662-663` fire only `if week4_succeeded` (line 658). There is no timer/interval driving percentage; `update_research_progress`'s monotonic `WHERE progress_percent <= :new` guard (`repository.py:1295`) additionally makes backward/out-of-order regression structurally impossible even if a caller tried. Frontend explicitly tests this contract: `ProcessingPage.test.tsx:69-83` ("never grows the percentage client-side between polls").

**Q6 — Provider/model server-fixed, not client-overridable.**
`ResearchRequest` (Pydantic model, `comqutor_alpha/api/routes_research.py:1251-1267`) has fields `ticker, analysis_date, selected_analysts, offline_raw_agent_outputs, run_id, force_refresh` only — no `provider`/`model`/`config`/`llm_provider` field exists on the model at all, and FastAPI/Pydantic's default `extra="ignore"` behavior silently drops anything else in the JSON body. The real config is built exclusively server-side from the single fixed `ACTIVE_PROFILE` (`comqutor_alpha/research_profiles.py:62-74`), applied on top of `TradingAgents.DEFAULT_CONFIG` (`research_profiles.py:121-148`), never touching the HTTP payload. `build_server_execution_context` (`comqutor_alpha/server_execution.py:201-278`) is the only source of `config`/`execution_identity` fed into execution — and `execution_payload["config"] = real_config` in `research_lifecycle.py:766` is set from `real_config` resolved in `prepare_research_submission`, never from `payload`.
Verified empirically, not just read: existing test `tests/test_research_profiles.py:175-215` (`test_http_model_and_config_fields_cannot_override_the_profile`) POSTs a real HTTP request via `FastAPI TestClient` with `llm_provider="evil-provider"`, `quick_think_llm`, `deep_think_llm`, `backend_url`, `config={"llm_provider":"evil"}`, `allow_real_tradingagents_run=True` all stuffed into the JSON body, and asserts the request is processed as an ordinary submission (only failing because the job manager was stopped for the test) — i.e. every injected field is silently dropped, never honored. **PASSED** (once DB env pollution is isolated — see §5/§7).

**Q7 — "Completed" requires the full Week 1-4 chain, not partial/degraded output.**
`build_research_response`'s status derivation (`comqutor_alpha/api/routes_research.py:399-404`):
```
if complete and structure_graph_ready and conflict_status == "ready":
    status = "completed"
elif complete or has_any:
    status = "partial"
else:
    status = "failed"
```
`complete` requires every `REQUIRED_COMPLETION_ARTIFACTS` (Week 1-2) to exist (`routes_research.py:372`); `structure_graph_ready` requires the Week 3 status marker to say `"success"` AND the graph artifact to exist (`routes_research.py:378`); `conflict_status == "ready"` requires Week 4's conflict pipeline to have actually persisted (`_run_week3_graph_pipeline`'s `week4_succeeded` gate, `routes_research.py:646-663`). A Week 3 failure, or a Week 3 success followed by a Week 4 failure, both degrade to `"partial"` — confirmed in the inline comment at `routes_research.py:390-398`. This mirrors exactly into `mark_research_run_terminal(run_id, status=result_status)` where `result_status` comes straight from this computed `status` (`research_lifecycle.py:858-862`).

## 3. Actual frontend behavior per question

**Q8 — Single run_id source of truth.**
Every one of the four pages pulls `run_id` exclusively from the React Router URL param via `useParams<{ runId: string }>()` — `ProcessingPage.tsx:160`, `ResearchRunPage.tsx:20`, `StructureGraphPage.tsx:50`, `ConflictRadarPage.tsx:65` — and routes are declared with `:runId` in `App.tsx:16-19`. No page reads a run_id from component state, a ref, or a prop passed down from a sibling; there is no cross-page shared store to drift. `ResearchPage.tsx:159` is the only writer (via `navigate`), and it always encodes the freshly-returned `result.run_id`.

**Q9 — Refresh mid-run recovers from server, not stale/blank UI.**
Because run_id lives in the URL (not memory), a hard refresh remounts the page, `useRunPolling(runId)`'s effect (`useRunPolling.ts:96-115`) fires immediately with the URL's `runId`, and `useResearchRun`/graph/conflicts hooks likewise re-fetch from scratch (`useResearchRun.ts:55-66`, `StructureGraphPage.tsx:21-44`, `ConflictRadarPage.tsx:20-43`). `ProcessingPage.tsx`'s own docstring/test assert this explicitly: `ProcessingPage.test.tsx:202-206` ("restores the run purely from the URL run_id").

**Q10 — Completed navigates to results; failed shows an error state, not a broken page.**
`ProcessingPage.tsx:205-211`: a `useEffect` keyed on `[runStatus, runId, navigate]` fires only `if (runStatus !== "completed" ...)` returns early, else waits 1200ms and calls `navigate(.../research)`. Failed status renders an `ErrorPanel` with `record.message`/`error_code`, Retry/Refresh/Return actions (`ProcessingPage.tsx:295-329`) — it never navigates anywhere. `ResearchRunPage.tsx:90-98` similarly renders a dedicated `run-failed-panel` with a "Back to Research" link and, critically, `shouldLoadResult = terminal && currentStatus !== "failed"` (`ResearchRunPage.tsx:32`) — the canonical-result/agent-outputs fetch is *never even attempted* for a failed run, so there's no possibility of rendering a broken/empty results page. Partial gets its own distinct treatment (`ProcessingPage.tsx:283-293`: explicit "finished only partially" copy + "Open partial results" link, no auto-navigate).

**Q11 — Polling cleanup correctness.**
`useRunPolling`'s `useEffect` depends on `[runId]` only (`useRunPolling.ts:96-115`); its cleanup sets `mountedRef.current = false`, clears the timer, and aborts `abortRef.current` (`useRunPolling.ts:109-113`) — this runs *before* React re-invokes the effect body for a new `runId`, and the new effect body additionally re-aborts/re-clears defensively (`useRunPolling.ts:97-103`) before starting a fresh fetch. Crucially, the async continuation in `runFetch` (`useRunPolling.ts:58-94`) checks `controller.signal.aborted` where `controller` is the **locally-closed-over** `AbortController` from that specific invocation (`useRunPolling.ts:61-67,80-83`), not `abortRef.current` — so even if `abortRef.current` has already been reassigned to a newer controller by the time an old request's promise settles, the old callback still correctly no-ops. This closes the classic stale-closure bug by construction, not by accident.
