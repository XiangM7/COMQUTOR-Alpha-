# D1：适配器校验器要求 `cited_source_id`，冻结 prompt 没有要求，离线定位

**结论**：这是 T1 来源关联改动（2026-09-28）留下的**接口契约缺口**，不是接线错误，不是消费错误，也不是模型质量问题或产品选择。
- 正确的修复需要修改冻结的 prompt，本轮禁止修改，所以**没有修**。
- 本轮没有改任何生产代码。
- 证据只用第二次 Fresh 保存的真实请求和回复。第一次 Fresh 作为补充。
- 复现走的是未改动的生产代码，零外部调用（网络陷阱拦截 0 次）。

## 3. 用原生产路径离线复现

**做法**（`tools/d1_offline_reproduction.py`，在网络陷阱下运行）：
- 使用：
  - 生产网关构建器 `build_server_week2_llm_gateway`；
  - 真实语义会话；
  - 未改动的 `_llm_batch_enrichment`；
  - 本 run 的来源登记。
- 唯一替换的是底层 HTTP 传输，它用线路审计里保存的回复体作答。
- 账本写在临时目录，不写入 run。

| 批 | 生产代码重建的请求 | 生产路径结果 | 校验器原消息 | 诊断对照：每条补 `"cited_source_id": null` |
|---|---|---|---|---|
| seq 8（按时返回，30 条） | 与当时发出的请求正文逐字节相同 | 富集未被采用；账本 `rejected` / `WEEK2_LLM_VALIDATION_FAILED`；回退确定性抽取，与 run 一致 | `enrichment item fields do not match the strict schema` | 整批通过，30/30 |
| seq 1（超时后才到，64 条） | 与当时发出的请求正文逐字节相同 | 假如按时到达，同样被拒，原因相同 | 同上 | 整批通过，64/64 |
| seq 7（未发送） | — | 传输层收到 0 次，预算占用 0；账本 `WEEK2_LLM_INPUT_TOO_LARGE` | — | — |

**关于诊断对照**：
- 只补一个 null 值，表示“不引用任何来源”。
- 它只用来判断缺字段是不是唯一的阻断点。
- 它不是修复，不写入任何 run，也不填任何来源 ID。

**结论**：第二次 Fresh 中拿到回复体的两批，**缺 `cited_source_id` 是唯一的阻断点**，其余校验都能通过：
- 逐字保留 claim、evidence、source_section；
- 段 ID 一一对应；
- direction、confidence 合法。

**补充：第一次 Fresh**（`d1_fresh1_supplementary.json`）共 5 批有回复，第一失败点都是这个字段：
- 补 null 后，3 批整批通过（64、34、25 条）；
- 另 2 批仍各有 2 条 `invalid direction`，即使补了字段，也会整批被拒（seq 7、seq 8）。
- 所以 Round 32 写的“第一次 Fresh 的 5 个返回也都是这样被拒”只说明了第一失败点，**不能推出补了字段就会全部通过**。
- 另外：第一次 Fresh 的 seq 1 按最终保存的来源登记重建请求，会多出 1 个候选来源。当时请求里只有 1 个，差异只在请求上下文，不影响对该回复的校验结论。

## 4. 能证明什么、不能证明什么

| 项 | 判断 |
|---|---|
| 当前校验器会拒绝严格按 prompt 作答的回复 | **能证明**（代码事实）：校验做的是集合相等比较；只含 prompt 要求的 8 个字段的回复，一定在第 1049 行失败 |
| 两次 Fresh 实际收到回复体的 7 批 | **观察到**：都只有这 8 个字段，都在这一步失败 |
| “所有回复必然被拒” | **不能这样写**。模型可以在未被要求的情况下自己加上这个字段。另外，第一次 Fresh 有 2 批即使补了字段也会因 direction 不合法被拒 |

## 5. 字段应该由模型提供，还是由调用上下文传递

**应由模型提供**：模型在本次请求提供的候选来源中选择，后端校验它是否属于这批候选。依据是 John T1 第 B 条和适配器的设计。

**调用上下文不能代填**，原因有三：
- 候选来源按**批**汇总，是本批所有段落匹配结果的并集，不是逐段的事实。第二次 Fresh 各批分别有 0、1、0、3、0、1、0、4、4 个候选，每批 27–64 段。
- 用上下文去填，就是替模型猜来源，或把候选批量挂到每一段上。这两种做法本轮都禁止。
- 逐条的确定性来源关联（原文标记、内容匹配、数字归一）已经单独运行，并用各自的方法名记录，不能记成 `AGENT_CITED`。

## 6. 为什么本轮不修，影响是什么

**正确的修复**：
- 在任务说明中要求模型返回 `cited_source_id`（只能取本次候选中的 ID 或 null）；
- 按 ADR-005，为 prompt 和输出 schema 升版本。

这需要修改冻结 prompt，**本轮禁止**。

**其他做法都不是正确修复，而且也在禁止范围内**：
- **把缺字段当作 null 放行**：
  - 这改变了 T1 设定的严格字段要求，属于核验要求；
  - 模型仍然不会给出引用，John T1 第 B 条要求的“结构化输出引用已有 ID”仍然不成立；
  - 送进 Alpha 分类的输入也会改变。
- **由上下文代填**：见第 5 节。

**当前影响**（第二次 Fresh）：
- 适配器的模型富集一次也没有被采用。
- 951 条 claim 的 entities、factors、direction、confidence 都来自确定性抽取。
- 来源关联由确定性方法完成，从不出现 `AGENT_CITED`。
- 9 批中只有 1 批是因为 D1 被拒（30 段）。另外 7 批超时、1 批输入超限，是**另外的问题**，D1 解释不了，修了 D1 也不会消失。

**离线证明与真实效果分开说明**：
- 离线已经证明：缺字段是第二次 Fresh 中两份回复的唯一阻断点。
- 修复后适配器富集会被采用多少、对 Alpha 分类有什么影响，没有真实调用就无法知道。
- 本轮不安排任何真实执行。
