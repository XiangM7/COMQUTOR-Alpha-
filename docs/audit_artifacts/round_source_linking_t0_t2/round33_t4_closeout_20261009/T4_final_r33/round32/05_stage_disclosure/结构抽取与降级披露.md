| 调用 | 原始回复（`content`） | finish_reason | 解析 | 校验 | 失败位置 | 判定 |

## 2. 适配器（claim 富集）

**9 批的结果**：

| 结果 | 批数 | 说明 |
|---|---|---|
| 超时 | 7 | 其中 attempt 2 在 45 s 后才收到 200 回复，客户端已按超时处理 |
| 输入超限，没有发送 | 1 | — |
| 返回但校验失败（`WEEK2_LLM_VALIDATION_FAILED`） | 1 | attempt 8，fundamental_agent，30 段 |

**哪些字段来自哪里**：
- 951 条 claim 的 `extraction_method` 都是 `deterministic_splitter`（`llm_record_count` 0）。
- 所以 entities、factors、direction、confidence、cited_source_id **全部来自确定性抽取，没有一个来自模型**。
- 其中 direction 为 `unknown` 的 504 条表示"没有判断"，**不是模型判断为 unknown**。

**发现的工程缺陷 D1（未修复）**：
- 适配器校验器 `_validate_llm_batch_enrichment` 要求每条回复必须恰好有 9 个字段，其中包括 `cited_source_id`。
- 但冻结的任务说明（prompt `week2.claim_batch_enrichment.v1`，sha256 `c6822099…`）只要求 8 个字段，**从未要求 `cited_source_id`**。线路审计中发出的请求原文也没有这个字段名。
- attempt 8 的 30 条和晚到的 attempt 2 的 64 条，每条都是 8 个字段，校验失败点都是 `enrichment item fields do not match the strict schema`。
- 离线定位、能证明与不能证明的范围、修复为什么超出当前边界，见 `round33/01_d1/D1_离线定位.md`。该文更正了本段原有的两处说法：
  - “严格按 prompt 作答的回复必然被拒，适配器富集永远走回退”只对严格 8 字段的回复成立；
  - “第一次 Fresh 的 5 个返回也都是这样被拒的”只说明第一失败点，其中 2 批即使补了字段也会因 direction 不合法被拒。

## 3. 降级披露（本轮新增）

`comqutor_alpha/api/stage_disclosure.py`：
- 从 run 自己的账本和阶段产物逐阶段统计：调用数、HTTP 数，以及结果中被采用、超时、未发送、回复未被接受、合法空结果的各有多少。
- 状态取值：`model_complete`、`degraded`、`model_not_used`、`not_run`、`not_recorded`。
- 适配器阶段列出哪些字段来自确定性处理。
- Graph 构建（`built`）与模型结构抽取分成两个阶段，各自报告。
- run 的 `completed` 含义不变：流程跑完，且 Alpha 分类没有调用故障。是否完成的规则没有改，也没有规定"任一超时就判整个 run 失败"。

**披露出现的位置**：

| 位置 | 内容 |
|---|---|
| API | `GET /api/research/{run_id}` 新增 `stage_disclosure` 字段。历史 run 也能读，读的是账本，不改写记录 |
| 页面 | Research summary 下方的 "Processing completeness" |
| Export | 本轮之后完成的 run 在收尾时写入 `stage_disclosure.json`，列入 manifest，进入 Export，内容与 API 完全一致（端到端测试和派生执行都验证了）。两次 Fresh 的历史 Export 不改，它们的披露由 API / 页面在读取时给出 |
| 摘要 | Research summary 区域显示披露要点（notes） |
