# "未发送却记为 malformed_response" 的修复

## 真实发送边界（代码顺序）

`Week2LLMGateway.invoke_json_with_trace` 依次执行四步：

| 步骤 | 内容 |
|---|---|
| 1 | 序列化 payload：`json.dumps(payload, ensure_ascii=False, default=str)` |
| 2 | 查同 run 缓存 |
| 3 | **长度超过 60,000 字符时立即返回** `provider_status=not_called`、`error_code=WEEK2_LLM_INPUT_TOO_LARGE` |
| 4 | 之后才进入请求循环：先占用预算（`_reserve_call`），再经审计传输层发出 HTTP |

所以输入超限的请求是本地拒绝：
- 没有预算占用；
- 没有 HTTP 请求和线路审计行；
- 没有回复、usage 或费用。

第二次 Fresh 的数据与此一致：网关预算占用 1204 次，等于账本 HTTP 尝试 1204 次。6 个未发送的调用都没有尝试，也没有审计行（`not_sent_appendix.json`）。

## 原来错在哪里

`content_support_llm._reason_from_invocation` 和 `evidence_stance_llm._reason_from_invocation` 把 `WEEK2_LLM_INPUT_TOO_LARGE` 和真正的格式错误（`WEEK2_LLM_INVALID_JSON`、`WEEK2_LLM_VALIDATION_FAILED`）一起归到 `malformed_response`。
- 页面和 Export 因此显示"模型回复格式不对、未被接受"，但这些请求根本没有回复。
- 适配器（原样记录 `WEEK2_LLM_INPUT_TOO_LARGE`）和 Alpha 分类（映射到 `input_too_large`）本来就是对的。

## 修复（最小范围）

| 位置 | 改动 |
|---|---|
| `content_support_llm.py`、`evidence_stance_llm.py` | 新增 `FALLBACK_INPUT_TOO_LARGE = "input_too_large"`。沿用 `alpha_mapper` 已有的同名原因码，没有另起体系。`WEEK2_LLM_INPUT_TOO_LARGE` 映射到它；真正的格式错误仍是 `malformed_response` |
| `content_support_llm.py` 的 attempt_log | 记录实际输入大小 `input_chars`、上限 `input_limit_chars`、`provider_attempt_count=0` |
| `week2_llm.py` | `Week2LLMInvocation` 新增 `input_chars`、`input_limit_chars`（仅本地拒绝时有值）。语义账本 `error_message` 写入："not sent: input of N characters exceeds the 60000-character limit; refused locally before any budget reservation or HTTP request (no provider response, no usage)" |
| `llm_runtime/session.py` | `finalize_call` 增加可选参数 `error_message`，只有网关给出时才传，其他调用不变 |
| `direction_evaluation.py` | "整批没有拿到回复"的原因集合加入 `input_too_large` |
| `api/evidence_trace.py` | 页面和 API 的解释文字："not sent: … exceeded the local input-size limit and was never sent to the model (no response, no usage)" |

**状态不变**：
- claim 的内容核验状态不会因此变成 NONE、"不支持"或"支持"，仍保持核验前的状态。在第二次 Fresh 中这 5 条都是 PENDING_REVIEW。
- 证据追溯归入 `TECHNICAL_INCOMPLETE`（技术未完成），不是模型判断。

**API、页面、Export 的一致性**：
- 新 run 中，原因码写在记录里，API、页面、Export 读到的是同一个字段。
- 阶段披露 `stage_disclosure` 直接从账本判断"是否发送"（`request_attempts` 为空且错误码为 `WEEK2_LLM_INPUT_TOO_LARGE`），所以历史 run 也能正确披露为"未发送"，不需要改写历史记录。

## 测试（只替换底层 HTTP）

`tests/test_t4_round32_not_sent_and_stage_disclosure.py::test_saved_oversized_request_is_not_sent_and_the_saved_sent_request_behaves_as_before`

**测试走的路径**：
- 生产网关构建器，加真实语义会话，加未改动的 `_process_batch`；
- 请求项由生产函数 `build_content_support_request_items` 从第二次 Fresh 保存的 claim 和来源登记重建，payload 与该 run 账本中记录的 payload **逐项相等**（241 个内容核验调用全部相等，在开发时核对过）；
- 合法请求的回复是该 run 线路审计中保存的真实回复体。

**断言**：

| 请求 | 断言 |
|---|---|
| 超限请求 | 传输层收到 0 次；预算计数不变 |
| 合法请求 | 传输层收到 1 次，预算 +1，结论与 Fresh 当时保存的一致，`error_message` 为空 |
| 账本 | `not_called`、0 次尝试、usage 全空、`error_message` 写明实际字符数和 60,000 上限 |
| claim | 原因为 `input_too_large`；状态仍是 PENDING_REVIEW；没有模型判定明细 |
