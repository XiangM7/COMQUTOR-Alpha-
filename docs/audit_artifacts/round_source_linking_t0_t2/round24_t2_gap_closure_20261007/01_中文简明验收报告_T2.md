## 2. 统一入口怎么执行契约规则

入口：`scripts/run_formal_acceptance.py` → `formal_acceptance_report.py` → `acceptance_engine.run_formal_acceptance` → 新模块 `gold_contract_rules.py`；生产写入器 `formal_acceptance_artifact.py` 调的是同一个函数。

* **契约按原样处理**：适用对象（标的）、run 绑定、版本（`gold_operational_contract.v0.2`）、触发、允许等级（契约的检测权威：`run_audit.json → activation_summary.per_alpha[alpha].level` 属于 `active／dominant／regime_level`）；**不加任何额外阈值**。
* **触发**：只对冻结矩阵实际绑定的 run 使用冻结触发；其它 run **没有已批准、可执行的判定方法**，就是 `not_evaluable`（`RUN_NOT_BOUND_TO_FROZEN_TRIGGER_MATRIX`），**不借用历史的 TRUE／FALSE**。
* **四件事分开记录**：① Alpha 是否被识别（有多少条 claim 被分类到它）② 实际激活等级与分数 ③ 契约要求是否满足 ④ 证据触发是否成立。“识别了但等级未达”≠“模型没有识别”；分类技术上没做完（`unavailable`）≠有效的 NONE，写 `CLASSIFICATION_INCOMPLETE_NONE_NOT_VALID`，不断言漏检。
* **严重度与汇总**：blocking／non-blocking 按契约；总状态沿用原规则（有 failure→fail，有 review／not_evaluable→needs_review，否则 pass）；`release` 块里只有 **blocking 的 FAIL** 才 `blocks_release`，non-blocking 永不拦截发布；`release_status` 是 `blocked／unresolved／no_blocker_among_executed_rules`，**明确不是认证**。
* **Gold 只在研究完成之后使用**：守护测试保证研究路径不 import 标签和契约模块，验收产物不被读回研究；研究产物未被改动。
* **`effective_rules.gold_contract`** 记录：契约路径、sha256、schema／gold 版本、冻结状态、与冻结清单一致、触发矩阵路径／sha256／绑定 run、markdown 伴随文件状态、**实际生效的 5 条规则**（各带批准依据）和**未生效的 14 条**。六类规则族另有“已对齐执行／仅诊断／未执行”的状态表（`six_ticker/formal_acceptance_tables.md §1`）。
* **错误路径**：契约、冻结清单、触发矩阵缺失／损坏／版本不符／不是冻结的那份／检测权威不符／缺要执行的规则／类型未实现 → 每个标的 `config_error`＋原因码，不会变成 NOT_APPLICABLE 继续 PASS。
* **容器布局**：包装安装后 `docs/` 不在包旁，缺省位置找不到时再找 `<工作目录>/docs/audit_artifacts/…`（有测试）。

## 3. Conflict 误判的修复

**3.1 问题（`offline_repro/conflict_pair_defect/`，真实检测器＋真实 B2＋同一批合成输入，第 23 引擎 vs 本轮引擎）**：每边只有 1 条证据、分数 40<50、无标的特异支持——都是 B2 的正确拒绝——原来判 **fail**，现在 `not_applicable`（`b2_rejected`）；Alpha 从未被识别或停在 capped_active，对根本没进 B2，原来被放过成 `not_applicable`，现在 `not_evaluable`；唯一真正的遗漏（受控修改：记录写成 candidate、无拒绝原因，B2 做不出）仍是 **fail**，并且和正确拒绝不再同一个结果。

**3.2 现在每个对按它在 run 里留下的记录分六种**（不新写 B2 公式，只读 B2 已保存的状态、原因码、计数、分数）：

| 记录状态 | 含义 | 必须检出对的结果 |
|---|---|---|
| `admitted` | B2 准入 | pass |
| `b2_rejected` | B2 评估过并给出拒绝原因（如 1/1 条证据、分数不足、无标的特异支持） | `not_applicable`——**正确拒绝，不是漏检** |
| `rejected_before_b2_no_qualifying_evidence` | 检测器记录了某边没有合格证据，没进 B2 | `not_applicable`，不强制 |
| `not_evaluated_before_b2` | 进 B2 前因其它原因被拒（Alpha 未处在可准入状态等），B2 没判过证据 | `not_evaluable`（不是“无证据”） |
| `no_arbitration_record` | 这个 run 根本没记录这一对 | `not_evaluable`（不是“无证据”，也不是“条件满足”） |
| `b2_not_admitted_without_reason` | 满足 B2 检查的全部条件、却没准入 | **fail（漏检）**——生产 B2 写不出这种记录，只能用受控修改证明这项检查确实会报出 fail |

**3.3 四个概念分开**：允许评估（taxonomy）／允许准入（`allowed_conflicts`）／必须检出（`required_conflicts`，六个标的现在都是空）／必须成为主冲突（没有已批准规则；`run_bound_expectations` 只是未批准的历史观察）。引擎**不生成、不删除、不修改**任何实际 Conflict。

**3.4 组合规则（契约 Step 4 §13）**：触发 PRESENT 时——任一允许对已准入＝pass（不要求每个允许对都出现）；一个都没准入＝**REVIEW 并要求复核**（逐对列出 run 记录的状态与 B2 原因），不直接判系统错误；**例外**：某个允许对自己的 B2 记录没有拒绝原因却未准入（持久化产物已证明确定性违反契约）＝FAIL，按契约原严重度；准入了家族以外的冲突＝REVIEW（保留研究输出，转入复核）。
