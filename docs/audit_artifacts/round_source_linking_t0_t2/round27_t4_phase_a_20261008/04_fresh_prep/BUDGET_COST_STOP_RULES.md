# D. NVDA Fresh Run：请求预算、成本估算与停止规则（待负责人确认）

数据：`budget.json`（`tools/build_fresh_budget.py` 生成，零网络）。实例实际生效的数值以 `frozen_config.json` 为准，由运行中进程的 `/ready` 和进程环境读出。

**下面的上限是提案，由负责人确认。** 预算不保证够用，新 run 的 claim 数要等研究 agent 跑完才知道。

不会自动发生的事：
- 不自动提高上限，不自动重发；
- 实例重启后不续跑：启动对账把残留的 queued/running 标为 failed，不会恢复执行（V5 已演示）；
- 不自动发起第二次 Fresh Run。

页面上有一个"重试"按钮，那是用户手动操作，我不会点。

停止时保留的内容：
- run 目录中已经写下的产物，包括 raw agent 输出、逐次追加的 `llm_semantic_calls.jsonl`、`error_logs/` 线路审计，以及数据库中的 run 行。
- 如果是作业超时，Week 3/4 产物和 `llm_usage_report.json` 不会在完成阶段写出。事后可以用 `run_usage_report` 从 run 目录只读重建。

## 3. 停止条件和发起后我做什么

- **会自行停止的情况**：Week 2 上限、研究 agent 上限、作业墙钟、实例被停止。四种都保留部分产物，状态为 partial 或 failed，不会报成 completed。
- **"completed"的定义**：Alpha 分类没有真实故障，同时图、冲突、ticker 一致性、产物完整性都通过。有一次调用失败就是 partial。
- **收到"已启动"之后我只做观察**：
  - 确认 run_id，观察进度；
  - 核对日志、数据库、Export 和产物；
  - 不调参数、不重发、不重启实例、不发起第二次 run。
  - 只有负责人明确要求时，才停止实例。

## 4. 已知风险（不是保证）

1. **墙钟。** 内容核验在生产中串行执行，profile 设为单条、无并发。
   - 按 T3 中位耗时（42 s），1040 条 claim 约 2.2 小时；
   - 按 T3 最大耗时（82.5 s）且计数偏高，约 6 小时，**超过允许的最大作业时长 4 小时**，会被终止并记为 failed。
   - 这是产品决定项，见 `READINESS_STATUS.md`。
2. **claim 数超过约 1500 时**会触及 1800 上限，run 为 partial。
3. **适配器和结构抽取仍使用共享的 45 s 超时**（profile 只覆盖三个 T3 任务）。历史上适配器单次请求输出可达约 1.5 万 token，超时后会退回确定性结果。
4. **没有熔断。** 遇到 401/429 这类系统性错误时，生产路径不会整体停止：每次调用各自失败，直到用完上限。401 不计费，429 是限流。T3 驱动遇到这些状态会整体停止，生产路径没有这一条。
5. **数据源。** `.env` 中 `COMQUTOR_DATA_SANITY_ENABLED=true`，Fresh Run 会真实请求 Yahoo Finance；研究 agent 本身也会取数。这是 Fresh Run 的正常部分，在负责人点击之后发生。
