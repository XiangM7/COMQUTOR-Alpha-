## 2. 当前产品配置与拟执行配置的差异

逐项见 `B2_config_differences.md`。实际请求形状取自离线演练审计里的原始请求，见 `B2_config/actual_request_shapes.json`。

**与产品一致的部分：**
- 模型 deepseek-v4-flash；prompt 为当前的 content_support v2.1、alpha v7、stance v3，身份哈希已冻结。
- 客户端由 tradingagents `create_llm_client` 创建，类为 DeepSeekChatOpenAI；接口为 `https://api.deepseek.com/chat/completions`。
- 请求体只有 `messages`、`model`、`stream=false` 三个字段：max_tokens、thinking、reasoning_effort、temperature、response_format 都不发送，由服务端默认。DeepSeek 的回复里带 reasoning tokens，说明思考模式默认开启。
- Alpha 单条发送，方向 10 项一批；SDK 重试 0；Alpha 和方向并发 4，内容核验串行。

**与产品不同的部分（需随授权一并确认）：**

| 项目 | 产品现状 | 本次执行 | 依据 |
|---|---|---|---|
| 内容核验路径 | 5 条一批 | **单条** | 5 条一批时，本样本 4 批中有 3 批超过网关 6 万字符上限，会在本地被拒 |
| 内容核验超时 | 45 s（全任务共用） | **120 s（候选值）** | 没有任何已保存数据证明 120 s 内能完成 |
| 方向超时 | 45 s | **120 s（候选值）** | 已保存数据中没有一次方向请求在 45 s 后完成；120 s 不保证成功 |
| Alpha 超时 | 45 s | 45 s | 一致 |
| 应用层重试 | `.env` 中为 1，方向任务会被提到 2 | **0** | 本轮指示 |
| 语义缓存 | 每个 run 一个进程内精确缓存 | **无** | 40 条输入各不相同，且守卫限制每个输入只发一次，所以本次不会出现缓存命中 |
| 任务路由 | 一个网关，一个共享客户端 | 每个任务一个网关、一个客户端 | 为了分任务设超时；网关和客户端类与产品相同 |

如果产品要采用上述设置，需要：
- 代码层面支持按任务设置超时（目前只有一个共用超时）；
- 内容核验批大小可配置，或改为 1（目前是常量 5）；
- 把 `.env` 的 `COMQUTOR_WEEK2_LLM_MAX_RETRIES` 设为 0。

**这些都不在本次修改范围内。** 验证结果只代表"本次冻结配置下的表现"，不代表"当前产品配置通过"。

## 4. 启动命令、预检和停止条件

签署方式：复制 `B4_execution/authorized_plan_TEMPLATE.json`，填写 `authorized=true`、`authorized_by`、`authorization_reference` 和 `execution_id`；如果同时授权采集，再把 `collection.authorized` 设为 true。其他字段不要改。然后：

```bash
cd <仓库根目录>; source .venv/bin/activate
D=docs/audit_artifacts/round_source_linking_t0_t2/t3_joint_sample_driver.py
PLAN=/path/to/signed_plan.json; SHA=$(shasum -a 256 $PLAN | cut -d' ' -f1)
python $D preflight --plan $PLAN --work-dir /tmp/t3_preflight          # 零调用：全部计划检查 + 完整演练
python $D collect --authorized-plan $PLAN --plan-sha256 $SHA          # 仅当 collection.authorized=true；≤4 次请求
python $D predict --authorized-plan $PLAN --plan-sha256 $SHA          # 真实预测；≤70 次请求
python $D status  --execution-dir outputs/t3_joint_evaluations/<execution_id>
```

**发送前检查**（任一不符即不发送，退出码 3 或 4）：
- 计划文件的 sha256 与命令行一致；已标授权，且写明授权人；
- 样本清单、复核表、冻结请求文件的哈希与计划一致；
- 三个任务的 prompt 身份不变；
- 代码身份不变：HEAD、完整工作区差异、未跟踪的运行时源码、驱动文件哈希。**执行前请不要改动工作区，否则需要重新冻结、重新授权。**
- 用当前代码和数据重新推导 40 个 Alpha 输入哈希和 17 个内容核验输入哈希，必须与冻结文件完全一致；
- API 密钥环境变量存在（只检查是否存在，不读出、不打印）；
- 执行目录不能已存在：执行从不续跑，也从不重发；
- 执行前用固定回复把整条管线完整演练一遍，零网络。演练要求没有任何请求被拒、每个冻结输入恰好发送一次、每次发送都有请求审计、回复审计和账本记录。演练不通过，不发送任何真实请求。

**发送中的停止规则**（守卫位于真实网络之前）：
- 请求的 URL、字段、模型、prompt 前缀或输入哈希与冻结内容不符时：**不发送**，并停止之后所有任务的发送。
- 认证失败（401/403）、请求字段被拒（400/404/422）、限流（429）、请求审计或回复审计保存失败时：停止之后的全部发送。
- 5xx 和超时：如实记录为该条失败，继续后续请求，不重试。
- 单条结果不理想、超时或截断：照原样保存，不改 prompt 重试，不换样本补成功数。
- 任务失败不会变成有效的 NONE；方向失败时，确定性基线只作为带标签的诊断字段，不冒充 LLM 方向。
- 检查点 `checkpoint.jsonl` 在每次发出前和返回后各写一次（fsync）。`status` 汇总已发送、未发送、成功、失败、unknown 的数量。**unknown 不会被自动重发。**

**产物**（`outputs/t3_joint_evaluations/<execution_id>/`）：
- 计划副本、`rehearsal_report.json`、检查点；
- 每个任务的请求审计和回复审计：任务、claim、call/attempt 身份、原始请求、原始回复、模型、usage、HTTP 状态；
- Alpha 和方向的语义账本：prompt 版本、输入哈希、usage、失败原因；
- `task_audit.json`：内容核验逐请求记录；
- `progress_L1.json`、`progress_L2_L3.json`、`joint_predictions.jsonl`、`run_summary.json`。

采集结果放在另一个目录 `<execution_id>-materials/`：
- 每个回复原样保存，记录 URL、时间、状态码、sha256；
- 生成复核表补充件，供复核前交给复核人；
- 不写回旧 run，也不说成旧 run 当时已有的材料。
