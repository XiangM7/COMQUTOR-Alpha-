# NVDA run (034a0a60-430e-41f8-8321-03a11389707a): concurrent-audit-loss fix, and precise Week2 request reconciliation

## Part 1: concurrent-audit-loss fix

**Root cause** (confirmed via the actual exception-propagation path, not the architecture doc alone): `SemanticCallRecorder.append()` rejected a record whenever its `call_sequence` (assigned by `SemanticRuntimeSession` at call-**start** time, under `session.py`'s own lock, strictly increasing by start order) was not strictly greater than the previously-appended record's `call_sequence`. Under real concurrent dispatch (Week2 alpha_classifier's own default concurrency=4), a later-started call legitimately completes -- and reaches `append()` -- before an earlier-started one. That call's real, already-billed attempt then raised `RecorderIntegrityError("RECORDER_SEQUENCE_NOT_MONOTONIC")`, which `session.py`'s `finalize_call` catches generically (`except Exception as exc: self._mark_degraded("SEMANTIC_RECORDER_APPEND_FAILED", exc, incomplete=True); return False`) -- silently dropping that attempt's entire audit record.

**This run's own, concrete, traced consequence** (not just the general architecture claim): the same `validate_semantic_call_records` cross-record check that rejects non-monotonic `call_sequence` is *also* called by `SemanticRuntimeSession.finalize_session` -> `self.recorder.verify_integrity()` (setting `SEMANTIC_RECORDER_INTEGRITY_FAILED`) and again by `build_semantic_manifest` -> `_read_calls` (raising `ManifestIntegrityError`, caught by the outer `except Exception as exc: self._mark_degraded("SEMANTIC_MANIFEST_FINALIZATION_FAILED", ...); return None`). This is why `llm_semantic_manifest.json` was never written for this run at all, confirmed by direct code trace, not inference.

**Fix**: a new field, `persist_sequence`, assigned by the recorder itself inside `append()` (under its own lock, in true append/completion order) -- never supplied by the caller, so no record can ever violate it; nothing to validate, only to assign. `call_sequence` is kept, unchanged, as the call's own start-order identity field, but is no longer used as any ordering gate at append time. The cross-record validator (`contracts.py::validate_semantic_call_records`, and its independent duplicate in `source_bundle.py::_call_collection_errors`) now checks `persist_sequence` monotonicity when present, falling back to the original `call_sequence` check only for pre-fix records that lack it entirely -- so existing, already-validated historical artifacts keep validating exactly as before, no backfill required. Duplicate `call_id`, wrong `run_id`/`execution_mode` are completely untouched.

**Diff**: `docs/audit_artifacts/round_source_linking_t0_t2/concurrent_audit_loss_fix.patch` (recorder.py, contracts.py, source_bundle.py, and the two updated/two new test files below).

**Targeted tests only, all passing** (204 in `tests/test_week2_llm.py` + `tests/llm_runtime/` + `tests/replay/`, 9 in `tests/llm_runtime/test_recorder.py` specifically):
- `tests/llm_runtime/test_recorder.py`: the two tests that previously *asserted the bug as correct behavior* (`test_non_monotonic_sequence_is_rejected`, `test_concurrent_calls_are_serialized_and_never_create_partial_lines` -- the latter literally asserted `outcomes.count("RECORDER_SEQUENCE_NOT_MONOTONIC") == 7`) were rewritten, not deleted, to assert the correct behavior with full justification in their own docstrings: out-of-order `call_sequence` is now accepted and `persist_sequence` reflects true append order; 8 genuinely concurrent threads now all persist (0 rejected), with strictly-increasing, gap-free `persist_sequence`.
- `tests/test_week2_llm.py` (real Gateway -> Session -> Recorder path, fixed/fake Provider responses, zero real Provider calls): `test_later_started_call_completing_first_does_not_lose_either_audit_record` (the exact incident scenario -- call 1 starts first, is deliberately blocked until call 2 fully completes and persists; both records survive, `call_sequence` ordering is preserved as the true start order while `persist_sequence` correctly shows the inversion); `test_concurrent_success_timeout_and_retry_all_preserve_their_own_attempts` (three concurrent logical calls -- one immediate success, one timeout-then-retry-success, one immediate success that is held back to finish last by start order but first by completion -- all three persist, the timeout+retry call's both real attempts are both intact, `gateway.call_count == 4` confirms budget counting is unaffected, and `validate_semantic_call_records` -- the same validator Exact Replay and manifest-building use -- accepts the result).

|---|---|---|---|
| Configured budget ceiling (`COMQUTOR_WEEK2_LLM_MAX_CALLS`) | 700 | this run's own exported env var | certain (this run's own config) |
| Budget ceiling was reached and enforced at least once | yes (1 log line) | `WEEK2_LLM_CALL_BUDGET_EXHAUSTED` in `error_logs/week2_llm_errors.jsonl` | certain, but this is a **one-time, deduplicated** flag (`_log_budget_exhausted_once`) -- it proves the ceiling was hit, it does **not** itself count how many subsequent calls were refused |
| Logical-call attempts refused *before* reserving/sending, because the ceiling was already exhausted | 400 | `alpha_matches.json`'s own `reason` field, `"llm semantic classifier unavailable: call_budget_exhausted"` | certain (persisted, per-claim) -- these consumed **zero** budget slots (`_reserve_call()` only increments on success) |
| Real attempts fully recorded with complete per-attempt detail | 448 | sum of `len(request_attempts)` across the 438 recorded rows with `provider_status in {success, timeout}` (400 `budget_exhausted` rows are excluded -- they made zero real attempts despite being logged) | certain (persisted, per-attempt, including the 10 rows that needed their one allowed retry) |
| Real attempts whose own audit record was lost (the bug fixed in Part 1) | **approximately 240** | count of `"semantic runtime degraded (... reason_code=SEMANTIC_RECORDER_APPEND_FAILED ...)"` lines in the launcher process's captured stdout | **not certain** -- this source is explicitly documented elsewhere in this codebase (`comqutor_alpha/regression/recorder_health_diagnostics.py`) as `EPHEMERAL_LOG_ONLY`, never a persisted/canonical artifact; no run-scoped file records this count. Each of these **is** a real, billed Provider attempt (the recorder failure happens strictly after the real attempt, in `finalize_call`) -- only its own detailed trace (token usage, finish_reason, per-attempt history) is unrecoverable, not the fact that the attempt happened. |
| Reconciled total real requests sent (448 + ~240) | **approximately 688** | derived, not directly observed | consistent with, and bounded under, the 700 ceiling -- the ~12-unit gap to 700 is not independently resolvable from available artifacts (the exact moment of exhaustion is not finely logged beyond the one-time flag above) |
| Known total tokens (input+output) from the 448 fully-recorded real attempts | 873,861 input + 158,633 output = 1,032,494 | `llm_semantic_calls.jsonl`'s own `token_usage` fields | certain, for exactly this 448-attempt subset |

**What this reconciliation explicitly does NOT do**: it does not treat 700 (the configured ceiling) as if it were the count of actual requests made (actual requests ≈ 688, a derived reconciliation, not an assumption that the ceiling was hit exactly); it does not merge the 400 budget-refused calls into either the "sent" or "lost-detail" buckets (they are a third, distinct category that consumed zero real Provider interaction); it does not estimate or backfill the ~240 lost attempts' own token usage into the known total.

## "Audit failure never affects canonical results" -- verified for this run specifically

Beyond the existing architecture proof (`recorder_health_diagnostics.py`, `session.py`'s own `finalize_call`/`finalize_session` call graph showing the recorder exception is caught strictly after each task caller has already fixed its own `invocation.validated_output`), this run's own real artifacts independently confirm it:

- `structured_agent_outputs.json` has exactly 1040 records; `alpha_matches.json` has exactly 1040 matches -- a 1:1 correspondence with **zero** claims dropped, missing, or duplicated, regardless of which underlying LLM calls had their audit trail lost.
- `alpha_matches.json`'s own `reason` field breakdown accounts for all 1040 claims exactly, across a closed, known set of reason codes (476 no-canonical-fit + 370 budget-exhausted + 137 selected + 32 positive-requirement-gate + 9 invalidation-gate + 7 truncated + 6 timeout + 3 provider-error = 1040) -- no anomalous, corrupted, or unaccounted-for entry exists anywhere in the canonical output, which is exactly what "audit-trace-only" predicts and what a real canonical-result corruption would **not** look like.
