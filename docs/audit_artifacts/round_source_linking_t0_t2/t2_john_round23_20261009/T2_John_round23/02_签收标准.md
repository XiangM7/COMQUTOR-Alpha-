## 七、最终交付与签收标准

只提交一个统一交付包，沿用已有目录和文件名即可，但入口清单必须指向唯一版本：

| 交付部分 | 必须包含 |
|---|---|
| 代码与配置 | commit、diff、实际有效规则、taxonomy、运行配置 |
| 来源验证 | AMD 固定问题清单、关键结论的来源关联与内容核查结果 |
| 测试与语义验证 | 原始样本、逐条预测、审核记录、自动生成的统计、测试日志 |
| 实际运行 | 完整 artifacts、原始调用记录、PostgreSQL 验证、Fresh Run metadata |
| 使用证明 | Demo 视频和一份可复制执行的 README |

README 不必很长，但应给出真实可运行的启动、回放和测试命令。不能只提供工程师电脑上的绝对路径、文件 hash 或统计摘录，而不提供被引用的实际内容。

### 本轮如何签收

**按任务分别签收，不要求所有报告都变成绿色 PASS：**
- 来源机制通过，必须同时有正确关联和内容支持的证据，不能只证明来源表已保存。
- 规则执行通过，必须有实际加载、运行和错误路径测试，不能只有配置副本。
- 语义验证必须对应实际模型配置，保留错误和覆盖限制。
- 环境验证必须在目标数据库执行，不能用旧测试记录代替。
- NVDA、QQQ 尚未关闭的具体争议继续单独记录，不能通过换一个成功 run 消除。

**若关键结论仍使用没有依据的证据，或规则缺失仍能产生正式 PASS，本轮相关任务就不能关闭。**

重点只有四个问题：

**改了哪段代码？用什么输入运行？实际结果是什么？还有什么没有通过？**

先把这四个问题用代码和原始记录回答清楚，再冻结内部 Demo 版本，不继续扩写“全部完成”的总结文档。
