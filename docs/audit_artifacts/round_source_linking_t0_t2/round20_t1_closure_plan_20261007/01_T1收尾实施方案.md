## 2. 四项判断与消费修正

### 2.0 总体机制（四项共用，避免建第二套系统）

```
Week 2 / 衍生 execution
 alpha_classifier（选择，不变）──► alpha_matches（规则字段原样）
        │
        ▼  仅对“已选 (claim, Alpha)”对
 evidence_stance_classifier  prompt v4（扩展既有任务，不新建任务）
        │   输出 5 个独立子块：stance／relevance／assertion／negation／subject，各自校验
        ▼
 apply_evidence_consumption_v2()   ← 唯一应用点（新模块）
   ① 原始规则结果保存到 rule_baseline（score／relation／assertion／stance，永不删除）
   ② 仅对“本子块已通过校验”的字段写入有效值，并标 *_authority
   ③ 确定性计算 subject_attribution 与 grounded_data_points
        ▼
 既有生产链（公式不变）：资格闸门 → Primary／Secondary → 事实分组(+依赖) → Activation v2 → 等级
                          → Conflict／B2 → Exposure → API／Export／UI
```

overlay 同步改写 `candidate_scores`／`top_candidates`／`eligible_candidates` 三处里同一 Alpha 的候选（JSON 往返后它们是三份拷贝，既有 A304／A501 修复的教训），并保持三处一致。

**三条硬规则**

* R1 子块缺失或失败 → 该字段保持旧规则结果，标 `unjudged_legacy_rule` 或 `incomplete:<原因>`，**绝不当作成功判断，也不默认为 1**。
* R2 只覆盖“已通过校验的子块”所对应的字段；一个子块失败不影响其他子块。
* R3 原始文本与原始规则结果永远保留；每个字段有 `*_authority`，正式消费用哪个版本一目了然。

**两份契约、一个开关**

* 判断数据契约 `alpha_evidence_judgment.v1`（模型产出 + 程序校验）；消费契约 `alpha_evidence_consumption.v2`（程序如何读）。
* `metadata.json` 与 `structure_graph.json` 顶层记录 `evidence_consumption_contract` ∈ {`legacy`, `v2`}；缺省 `legacy`。**没有应用 overlay 的 run，所有消费者看到的字段与今天逐字节相同**（4.3 用测试证明）。
* 为什么用 overlay 而不是逐个改消费者：relation／score／assertion／stance 被 Activation、冲突、Exposure、Evidence Integrity、API、导出多处读取（F2、F3、F4），其中 B2 在冻结守卫内；在 `alpha_matches` 一个点写入有效值，才能保证“同一份结果”而不触碰冻结文件。

**调用位置（两处，同一函数）**

1. Fresh Run：`alpha_mapper.build_alpha_matches_payload`（`:1220`，`apply_llm_stance_upgrade` 之后），受合同开关控制，新增可选参数 `sources`／`contract`。
2. 衍生 execution：执行器把 overlay 后的 payload 作为 `assembled_alpha_matches` 交给 `finalize_classification_recovery_execution`；该函数新增 `metadata_extras` 参数写入合同标记（目前 `execution_metadata` 无扩展点）。

### 2.1 语义相关强度

| 问题 | 方案 |

### 3.2 派生计算（毛利率等）

* **公式登记表 `derived_metric_formulas.v1`**：`pct_change`、`ratio`、`difference`；具名指标：毛利率＝Gross Profit÷Total Revenue，营业利润率，净利率，YoY，QoQ（行项目名取自已保存快照的 `all_line_items`）。
